# 二战风云 · 人机（AI 玩家）模块设计方案

> 目标：让一批「虚拟玩家」在游戏里**从零开始**自己发育——建城、升级建筑、研究科技、招募军官、造兵、打野地、占领采集，并在条件成熟时**主动宣战、攻击真实玩家**。
> 玩家侧看到的应该是一个「正常玩家」，而不是一个功能或 NPC。

---

## 一、需求拆解

| # | 需求 | 说明 |
|---|---|---|
| 1 | 人机城市 | 人机要有自己的城市，坐标落在地图上，和玩家城一样能被侦查/掠夺/征服 |
| 2 | 自己发育 | 建城 → 升级建筑 → 研究科技 → 招募军官 → 召集人口，全流程自己走 |
| 3 | 从头玩 | 从「列兵 + 1 级市政厅 + 5000 资源」的初始态开始，不靠作弊资源 |
| 4 | 造兵 | 按自己的兵种配比训练部队，能被打残后重新造 |
| 5 | 攻击玩家 | 会主动找目标、宣战、出征、掠夺/征服 |
| 6 | 可控 | 运营能开关、能调难度、能一键生成/清空 |
| 7 | **人机标识** | 家园号 + 二战库表都要带 `is_bot` 标识，真人数据与人机数据在**任何一层都能一刀切开** |
| 8 | **管理端独立** | 人机管理独立成一个模块，**与玩家管理分开**，方便日后维护 |

**一个明确的口径**：人机**不是**「寇城」的升级版。寇城是静态 NPC（打完就没了，不会发育、不会出兵）；人机是**有状态的玩家代理**，会成长、会积累、会记仇。

## 二、现状盘点（决定方案怎么落地）

### 2.1 可以直接复用的（这是本项目最大的优势）

| 已有能力 | 位置 | 对人机的价值 |
|---|---|---|
| 完整玩家数据模型 | `ezfy_profile` / `ezfy_city` / `ezfy_city_building` / `ezfy_city_troop` / `ezfy_user_tech` / `ezfy_officer` / `ezfy_order` | 人机直接落这些表，**零新玩法** |
| 完整玩家动作接口（80+ 个） | `router.go` 的 `ezfyG` 组 | 人机「想做的事」全都有现成接口 |
| 懒结算体系 | `refreshCity` / `processOrders` / `processArrive` / `calcResource` | 人机不用写任何"时间流逝"逻辑，调一次 `/view` 就等于"上线结算" |
| 后台循环先例 | `ezfyPeriodicReload`（30s tick + `sync.Once` 懒启动） | 人机 tick 直接照抄这个模式 |
| 出征/战斗/战报全链路 | `createOrder` → `settleDispatch` → `processArrive` | 人机打仗和玩家打仗走**同一条代码路径** |
| 数据清理框架 | `ezfy_admin_purge.go::ezfyPurgePlayerData` | 一键清空人机可以直接复用 |

### 2.2 缺口

1. **没有「机器人身份」概念** —— 家园库 `users` 无任何标记字段，无法区分人机与真人。
2. **没有多进程互斥** —— 项目是**两个服务进程共享一个 RDS**（见 `ezfyPeriodicReload` 注释），任何 `for range time.Tick` 都会**在两个进程里各跑一遍**。人机 tick 不做互斥 → 每个动作执行两次（重复造兵、重复出征）。
3. **没有决策层** —— 寇城的守军来自配置表，没有"看情况做决定"的逻辑。
4. **没有风控** —— 没有攻击节流、目标保护、难度分层。

### 2.3 必须先知道的硬约束（会直接决定 AI 行为）

| 约束 | 出处 | 对人机的影响 |
|---|---|---|
| **打玩家城必须先宣战，宣战 24h 后才生效，有效期 48h** | `ezfyWarDelayHours=24` / `ezfyWarDurationHours=48` | ⚠️ 人机**不能"看到谁就打谁"**。必须先锁定目标 → 宣战 → 等 24h → 再打。AI 必须有「宣战计划表」 |
| 免战保护令**双向生效** | `createOrder` 开头的出击侧拦截 | 人机打不了免战城；人机自己也可以被打上免战（默认不给它用） |
| 出征队列上限 = **出发城司令部等级** | `createOrder::marchingCnt` | 人机必须先升司令部，否则只能派 1~2 队 |
| 附属野地同时只能一队采集 | `openWildGather` | 人机铺采集点要排队 |
| 线上是 **1 核 1G + 跨 WAN 的 RDS** | 项目红线 | 人机的**每个动作都是昂贵 IO**，必须分批 + 错峰 + 复用批量接口 |
| 请求路径禁全图枚举 | 项目红线 | 人机找目标**不能**遍历 `ezfyWorldSize²` |

## 三、总体架构

三层解耦：**身份层**（人机是谁）→ **决策层**（人机想干什么）→ **执行层**（怎么干）。

```
┌──────────────────────────────────────────────────────────────┐
│ 身份层  Bot Identity                                          │
│  家园库 users(is_bot=1) ─┬─ ezfy_account(随机密码,禁止登录)      │
│                          └─ ezfy_profile + ezfy_city(初始主城)   │
└───────────────────────────┬──────────────────────────────────┘
                            │ user_id
┌───────────────────────────▼──────────────────────────────────┐
│ 决策层  Bot Brain（每 60s 一轮 tick，租约锁保证单进程执行）        │
│                                                              │
│  ① 取「到点该行动」的 bot（next_act_at <= now，分批 10 个）      │
│  ② 读局面：资源/建筑/部队/科技/军官/在途订单/战报               │
│  ③ 选动作：发育优先级队列 → 军事状态机                          │
│  ④ 写回 next_act_at（+ 随机抖动，模拟真人节奏）                  │
└───────────────────────────┬──────────────────────────────────┘
                            │ 内部调用
┌───────────────────────────▼──────────────────────────────────┐
│ 执行层  Action Executor                                       │
│  内部 HTTP 自调用 http://127.0.0.1:8080/games/ezfy/*           │
│  （复用 100% 现有校验 / 结算 / 战报 / 防抖逻辑）                  │
└──────────────────────────────────────────────────────────────┘
```

## 四、关键设计决策

### 4.1 人机身份怎么建？（方案 A：在家园库建「机器人账号」）

**做法**：
- 家园库 `users` 加一列 `is_bot tinyint default 0`（比"保留 uid 号段"更明确、更好查）。
- 同时建档：`ezfy_account`（`password` 填一个**随机不可登录**的 bcrypt 串）+ `ezfy_profile`（`game_uid` 用独立号段）+ `ezfy_city`（复用 `createMainCity` 的初始态）。
- 昵称从**词库**随机（"钢铁洪流""沙漠之狐""北境守望"…），保证唯一。

**为什么推荐 A**（而不是"只建二战侧档案"）：
- 统帅页 `PlayerInfo` 是**先读家园库 users**（`h.home().First(&u, target)`），没有家园行直接 404；
- 排行榜、战报里的玩家名、好友、邮件、私信、军团，全部靠 `user_id` 串起来 —— 只有家园行在，人机才**处处都是一个真玩家**。

**必须配套的隔离**：
- 登录接口（`EzfyLogin` / `EzfySSO` / 家园登录）遇到 `is_bot=1` 一律拒绝；
- 注册、改密码、找回等入口对 bot 段做拦截；
- 人机不进"充值/钻石"体系（`diamond` 恒 0，管理端不发）。

### 4.2 人机标识：家园库 + 二战库都要打标

规则：**家园号要有人机标识，二战库的表也要有对应标识** —— 目的是让「真人数据」和「人机数据」在**任何一层都能一刀切开**，运营统计、后台列表、日志排查都不串味。

**打标清单（三档，不是无脑全加）**：

| 档 | 表 | 加什么 | 为什么 |
|---|---|---|---|
| **必加** | 家园库 `users` | `is_bot tinyint default 0` + 索引 | 账号级**权威源**；家园后台用户列表、注册数统计都靠它 |
| **必加** | `ezfy_profile` | `is_bot` + 索引 | 二战侧**权威源**；所有「这个玩家是不是人机」的判定入口 |
| **必加** | `ezfy_city` | `is_bot` + 索引 | 地图渲染 / 目标筛选 / 城市统计**大量直接查 city 表、不 join profile** → 冗余一列最省事（线上 1 核 1G + 跨 WAN，join 很贵） |
| 建议加 | `ezfy_account` | `is_bot` | 登录路径性能敏感（每次登录都要判「人机不许登」），直接读本表列最稳 |
| 建议加 | `ezfy_corps` | `is_bot` | 若人机允许建军团，军团管理列表要能区分人机军团 |
| **不加** | `ezfy_order` / `ezfy_report` / `ezfy_officer` / `ezfy_city_troop` / `ezfy_user_tech` / `ezfy_city_building` / `ezfy_item` / `ezfy_equipment` / `ezfy_wildland` … | — | 这些表都靠 `user_id`/`city_id` 强关联，查询天然带 user_id → **在入口（profile/city）判一次就够了**。每张表都冗余一列，只会带来「改一处忘另一处」的漂移风险 |

> **判断标准（一句话）**：**有独立查询入口、查询时不带 user_id 的表才加列**；明细表一律不加，靠入口过滤。
> 这与项目现有原则一致：**规则只有一处实现**。

**一致性保障（必须做，否则两个标识会漂移）**：

- **权威源** = 家园库 `users.is_bot`；二战侧的 `ezfy_profile.is_bot` / `ezfy_city.is_bot` 是**副本**。
- **写入点唯一**：建人机走一个 `ezfyBotProvision()`（**单事务**：users + ezfy_account + ezfy_profile + ezfy_city 一次写完，`is_bot` 一起落）。管理端的「转人机 / 转真人」也走**同一个函数**，绝不各写各的。
- **断言测试**：扫 `ezfy_city.is_bot = 1` 的行，其 `user_id` 必须能在 `ezfy_profile` 找到 `is_bot = 1`；反向同理。漂移即测试失败（照抄 `ezfy_admin_purge_test.go` 的漏表护栏思路）。
- 建城函数（`createMainCity` / `replenishCity` / `CreateCity`）写 city 行时，`is_bot` **从 profile 取**，不要从请求参数取。

**"分开"带来的实际收益（不只是好看）**：

- **玩家信息管理列表自动排除人机**（`AdminEzfyPlayers` 加 `is_bot = 0`）→ 运营看到的「注册用户数 / 在线数 / 新增玩家」不再被几百个人机污染。
- 城市管理、地图管理、排行榜统计同理，都加一个「含人机」开关，默认**不含**。
- 人机自己的数据只在「人机管理」里出现，两个模块互不干扰。

### 4.3 动作怎么执行？（方案 A：内部 HTTP 自调用）

| 方案 | 评价 |
|---|---|
| **A. 内部 HTTP 自调用**（推荐） | 人机拿内部签发的二战 token，直接打 `http://127.0.0.1:8080/games/ezfy/*`。**零重复实现**，天然继承防抖、免战、宣战、兵力校验、战报、扣费原子性等全部规则。人机**不可能**做出玩家做不到的事 |
| B. 抽「业务内核」层（handler 与 bot 共调） | 最干净，但要重构 80+ 个依赖 `*gin.Context` 的 handler，改动面极大、回归风险高，**本期不做** |
| C. 直接调 `createOrder` 等内部函数 | 需要手搓 `gin.Context`，脆弱且易漏校验，**不采用** |

**要点**：
- token 走 `authutil.GenerateEzfyToken`，人机专用（不受单点登录 `session_at` 限制）。
- 走 `127.0.0.1`，不要绕公网。
- 维护模式 `EzfyMaintGate` 会挡住人机 —— 这是**期望行为**（维护时人机也停）。

**"懒结算"就是人机的免费午餐**：每轮先调一次 `/games/ezfy/view`（= 玩家上线），建筑完工、训练出厂、资源产出、订单到达全部自动结算到当前时刻。人机**不需要**任何自己写的时间逻辑。

### 4.4 调度与多进程互斥（最容易踩的坑）

```
每 60s：
  if !acquireLease("ezfy_bot_tick", 90s) { return }   // 租约锁，只有一个进程进
  bots := SELECT * FROM ezfy_bot WHERE enabled=1 AND next_act_at<=now LIMIT 10
  for each bot: bot.Tick()
  releaseLease()
```

- **租约锁**用一张单行表 `ezfy_bot_lock(owner, expire_at)` + **带条件原子 UPDATE**（`UPDATE ... SET owner=?, expire_at=? WHERE name=? AND expire_at < ?`，判断 `RowsAffected`）—— 与项目现有「带条件原子 UPDATE」风格一致，不引入 Redis。
- **分批 + 错峰**：每轮只处理 10 个，`next_act_at` 加随机抖动（例如 60s ± 30s），避免 1 核 CPU 被 100 个人机同时打满。
- 人机数量上限做硬卡（配置项，默认 50），防止误配 1000 个把人打死。

### 4.5 发育策略（优先级队列）

每个 tick 按顺序尝试，**第一个能做的就做，做完本轮结束**（一次只做一件事，最像真人）：

```
0. 收尾：结算在途订单 / 收战报 / 收采集
1. 保命：城内部队 < 防守线 → 造兵（优先级最高）
2. 人口：空闲人口 < 阈值 → 召集人口
3. 建筑：市政厅 → 民居 → 资源田 → 军工厂 → 司令部 → 仓库
   （按「当前瓶颈」动态排序，不写死顺序）
4. 科技：军事科技优先（攻击/防御/负重），其次经济
5. 军官：军官数 < 参谋部等级 → 军校招募 → 上阵
6. 兵：主力部队数量 < 目标 → 训练（按兵种配比）
7. 扩张：资源溢出且达到条件 → 起新城
8. 闲置：无正事 → 打野地升级 / 派采集队
```

**资源不足怎么办**：不"发钱"，而是**降级到能做的事**（打野地、派采集、调高开工率）。这是"从头玩"的关键——人机的成长曲线必须和真玩家同一条。

### 4.6 军事策略（含宣战前置的时序问题）

因为「宣战 24h 才生效」，AI 必须**提前规划**，用一张 `ezfy_bot_target` 计划表驱动：

```
状态机：
  侦察  → 选目标（战力比 / 距离 / 非免战 / 非同盟 / 非新手）
        → 写入计划表（status=待宣战）
  宣战  → 到点执行 POST /war/declare（个人宣战）
        → status=待生效（记录 effect_time）
  待生效 → 每轮检查是否已生效（24h 后）
  出击  → 生效后：派侦查机看家 → 主力掠夺/征服
        → 打赢：继续下一目标 / 打输：回发育（换更弱的目标）
  冷却  → 同一目标 X 小时内不重复打
```

**目标筛选（走索引，绝不遍历全图）**：
- 候选集来源：`ezfy_city` 按坐标范围查（`x BETWEEN ? AND ?`，走 `idx_xy`），**不是**遍历世界格。
- 过滤条件（全部下推 SQL）：战力低于自己 × 阈值、无免战（`ezfy_city_effect`）、非同盟/同军团、注册天数 > 保护期。

### 4.7 难度分层（运营视角很重要）

用三个参数描述一档人机，而不是写三套代码：

| 参数 | 作用 |
|---|---|
| `grow_rate` | 发育速度倍率（影响升级/造兵的"耐心"，不是作弊给资源） |
| `troop_target` | 目标兵力规模（决定它打谁） |
| `aggression` | 攻击性（0~100，决定它多主动宣战、打多强的目标） |

**档位**：新手陪练（弱、防守型）/ 普通（均衡）/ 精英（强、侵略性高）。

**开服调参**：支持「批量注入已发育到 X 级的人机」——否则开服第一天全是 1 级人机，起不到作用。这不是作弊，是运营初始化（和给玩家发开服礼包同理）。

| **标识字段（见 4.2）** | | |
| `users.is_bot` | 家园库：`tinyint default 0` + 索引 | 账号级**权威源** |
| `ezfy_profile.is_bot` | 二战库：`tinyint default 0` + 索引 | 二战侧**权威源** |

| `ezfy_cfg_bot` | （可选）管理端配置：档位参数、开关、节流阈值 | 也可以直接进 `ezfy_cfg_limit` |

## 六、红线与风控（不做这些就不要上线）

1. **总开关** + **「允许攻击玩家」独立开关**（可以只让人机发育、不打扰玩家）。
2. **攻击节流**：每个 bot 每日 ≤ N 次出征；同一真实玩家每日最多被 M 个人机攻击。
3. **新手保护**：注册 < X 天 或 战力低于阈值的玩家**不进目标池**（这条比什么都重要，新人被打跑就全完了）。
4. **不打免战城**（复用现有逻辑，天然满足）。
5. **性能**：分批 + 错峰 + 走索引选目标；复用现有批量接口（禁逐支打库 —— 见项目红线「批量接口禁逐支打库」）。
6. **可一键清理**：复用 `ezfyPurgePlayerData`，人机数据能连根拔掉。
7. **不参与真实经济**：钻石恒 0、不充值、不参与充值榜。
8. **可识别性**（运营口径可选）：管理端能看到 `is_bot=1` 标记；玩家端**默认不可见**（否则失去陪玩意义）。是否在战报里露馅，需要单独决策。
9. **数据不串味**：玩家管理、城市管理、统计报表、排行榜**默认必须排除人机**（`is_bot = 0`）；人机数据只出现在「人机管理」模块里。
10. **权限点必须入 `modulePerms` + `EnsureRBACPerms`**：`seed.skip: true` 下漏了这一步，就是「菜单看得见、点进去没权限」（见 7.4）。

## 七、管理端：人机管理与玩家管理**彻底分开**

规则：**人机管理要和玩家管理分开，方便日后维护**。做法是「前端菜单、前端组件、后端路由、后端 handler、权限点」五层全部独立，人机的东西**不塞进现有玩家管理页面**。

### 7.1 分层隔离清单

| 层 | 玩家管理（现有，不动） | 人机管理（新增，完全独立） |
|---|---|---|
| 前端菜单 | `menu.js` 的 `g-ezfy`（二战征途）→ `ezfyPlayers` 等 30+ 项 | **同一个 `g-ezfy` 组内**新增 **`ezfyBot`「人机管理」**（独立菜单项 + 独立组件） |
| 前端组件 | `AdminEzfy*.vue` | **新建 `AdminEzfyBot*.vue`**（不改现有组件） |
| 权限点 | `module:ezfyPlayers` / `module:ezfyCities` … | **`module:ezfyBot`**（独立权限点，可单独授权给运营） |
| 后端路由 | `/api/admin/ezfy-players` … | **`/api/admin/ezfy-bot/*`**（独立前缀） |
| 后端 handler | `ezfy_admin.go` / `ezfy_admin_ext.go` … | **新建 `ezfy_admin_bot.go`**（handler 仍用 `EzfyAdmin` 类型） |
| 数据 | `is_bot = 0` | `is_bot = 1` |

> 这样「日后维护」时，人机模块的改动**不会碰到任何玩家管理代码**；上线出问题也能整块回滚。
> **菜单位置已定：人机管理是「二战征途」组内的一个功能模块** —— 挂在 `g-ezfy` 组下（`menu.js` 里跟 `ezfyPlayers` 同级的一个 `key: 'ezfyBot'`），**不另起顶级菜单组**。

### 7.2 人机管理页面内容

| 页面 | 功能 |
|---|---|
| 人机列表 | 昵称 / 战力 / 建筑等级 / 兵力 / 最后行动时间 / 当前状态（发育中 · 宣战中 · 冷却）/ 单个启停 |
| 生成与清理 | 一键生成 N 个（选档位，可选「已发育到 X 级」）/ 一键清空全部人机（走 purge 框架） |
| 档位与节奏 | `grow_rate` / `troop_target` / `aggression` / 每档数量 |
| 风控配置 | 总开关、「允许攻击玩家」开关、每日节流、新手保护天数 |
| 行为日志 | 查某个人机最近做了什么、**为什么没动手**（排障利器） |

### 7.3 现有页面要做的「排除人机」改造

| 页面 | 改造 |
|---|---|
| 玩家信息管理 `AdminEzfyPlayers` | 列表加 `is_bot = 0`；**注册数 / 新增 / 在线数统计同步排除** |
| 城市管理 `AdminEzfyCities`、地图管理 `AdminEzfyMap` | 加「含人机」开关，**默认不含** |
| 排行榜 / 数据管理 `AdminEzfyData` | 统计默认排除人机（人机是否上榜是运营选项，见第六节第 8 条） |

### 7.4 ⚠️ 必踩的坑：权限点必须挂 `EnsureRBACPerms`

线上 `config.yaml` 有 **`seed.skip: true`** → `main.go` 整体跳过 `seed.Run` → 新加的 `module:ezfyBot` **永远不会进 `permissions` 表**，表现为**「菜单看得见、点进去报『你没有权限进入！』」**。

必须同时做两件事：
1. 权限清单加到 `seed.go` 包级 `modulePerms`（**唯一实现**）；
2. 在 `seed/rbac_ensure.go::EnsureRBACPerms` 里幂等补权限点，并给「补种前拥有全部权限」的全量角色追加（自定义角色不动）。

口诀：**`seed.skip` 下「加菜单」≠「加权限点」**。

### 7.5 复用 `EzfyAdmin` 类型时的注意点

挂新路由时**必须按「当前模块」重挂权限**（`perm(db, "module:ezfyBot")`），不要沿用 `module:ezfyPlayers` —— 否则「人机管理」会跟着玩家管理权限被一起授权，就失去「分开」的意义了。

## 八、分期实施

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0 基础设施** | 身份层（建号 / 建城 / **三处 `is_bot` 标识 + 一致性断言**）+ tick 循环 + 租约锁 + 动作执行器（内部 HTTP）+ **玩家管理列表先排除人机** | 人机在游戏里像个人、会**造兵**、重启不重复执行；**玩家管理列表里看不到人机** |
| **P1 发育 AI** | 建筑/科技/人口/军官/资源优先级队列 + 错峰节拍 | 人机 3 天内能自然发育到 10 级建筑，曲线和真人接近 |
| **P2 军事 AI** | 打野地 → 采集 → 宣战计划表 → 掠夺/征服玩家 | 人机能自己宣战并打下真实玩家城，战报正常 |
| **P3 管理端 + 风控** | **独立菜单「人机管理」+ 独立权限点 `module:ezfyBot` + 独立路由 `/api/admin/ezfy-bot/*`** + 开关/难度/节流/日志/一键生成清空 | 运营能自助调节；人机模块与玩家管理代码互不干扰，可整块回滚 |

**建议先做 P0 跑通闭环**（哪怕只有 3 个人机、只会造兵），确认"人机在游戏里像个人"之后再投 P1/P2 的复杂度。

## 十、一句话总结

**本项目做这件事的成本比一般项目低得多**：玩法、结算、战报、校验全都现成，人机本质上只是「一个自动操作的客户端 + 一个会做决定的脑子 + 一个防止重复执行的锁」。真正要花心思的不是"怎么让 AI 会造兵"，而是三件事：**怎么让它像个人**（节奏、难度、不欺负新人）、**怎么不让它把 1 核服务器打死**、**怎么让真人数据和人机数据在各层都不串味**（家园号 + 二战库统一标识、管理端独立模块）。
